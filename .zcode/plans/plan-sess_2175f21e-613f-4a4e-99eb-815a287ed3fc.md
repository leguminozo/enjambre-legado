## Arquitectura de compatibilidad Safari/iOS 15 — las 3 apps (nucleo, tienda, campo)

### Contexto honesto del diagnóstico
- iPhone 7 en **iOS 15.8** (confirmado). En esta versión existen `.at()`, `Object.hasOwn`, `dvh` y `:has()` (todas 15.4+), así que mi hipótesis inicial (APIs faltantes) **no aplica a este dispositivo**.
- Análisis estático del bundle de nucleo: sin regex lookbehind literales, sin import attributes, polyfills core-js para `Promise.withResolvers`/`toSorted`, `requestIdleCallback` y `randomUUID` con guardas. **El bundle debería correr en 15.8 — pero no puedo reproducirlo localmente** (no hay simulador de Safari 15 en este Mac) y el usuario reporta botones muertos.
- Conclusión: la causa real está sin verificar. La arquitectura debe **instrumentar primero** y luego fijar, con guardarraíles para que no se pudra.

### Fase 0 — Instrumentación de diagnóstico (desbloquea todo)
1. **Harness de error visible**: en `packages/ui`, componente `ErrorRevealHarness` (script inline server-safe) que captura `window.onerror` + `unhandledrejection` y muestra un panel en pantalla con mensaje y stack cuando ocurren errores. Se inyecta en las 3 apps. Deploy a preview de Vercel → el usuario abre en el iPhone 7 y reporta el error real (mensaje + stack). **Esto reemplaza la adivinanza por un hecho.**
2. **Auditoría de payload de la ruta /login**: medir el JS real que carga el login (¿three.js/leaflet/GSAP filtrados al login? → señal de rendimiento A9/2GB). Si hay pesos pesados, code-split.
3. **Regla de contingencia**: si el harness revela crash de memoria/Safari mata la pestaña (posible en 2GB RAM), el plan B es reducir payload del login o entry legacy estático — se decide con el dato del harness, no antes.

### Fase 1 — Capa de compatibilidad compartida (packages/ui)
4. **`legacy-browser-polyfills.tsx`** (patrón `ThemeInitScript`, server-safe): script IIFE con feature-detection y ~1.5 KB que cubre el piso legacy completo: `Array.prototype.at`, `Object.hasOwn`, `findLast/findLastIndex`, `Promise.withResolvers`, `structuredClone` (fallback JSON guardado), `String.replaceAll`. No-op en navegadores modernos. **Con unit tests** (vitest) que simulan APIs ausentes y verifican el polyfill.
5. Inyección en los 3 root layouts como primer elemento (corre antes que el JS de Next, que llega async).
6. **CSS fallbacks dvh→vh** (17 ubicaciones inventariadas): nucleo globals.css (4 reglas), tienda globals.css (3 reglas), 10 clases Tailwind en 9 archivos → `min-h-screen min-h-[100dvh]` (patrón canónico).
7. **`:has()` funcionales de tienda** (13 reglas): las de padding para `.tienda-cart-bar`/`.tienda-sticky-cta` se reemplazan por **selectores de data-attribute** (`[data-tienda-has-cart]`) que React ya conoce — funcionan en TODAS las versiones y eliminan la dependencia de Safari 15.4. La regla cosmética de nucleo (`.card:has(> table)`) se convierte igual o se elimina.

### Fase 2 — Guardarraíles (lo que la hace "largo plazo")
8. **Test empírico de browserslist+Turbopack** (go/no-go): agregar browserslist target Safari 15 a nucleo, rebuild, comparar bundle (downlevel de sintaxis + inyección de polyfills core-js). Si Turbopack lo respeta → adoptar en las 3 apps. Si no → la capa de compat (Fase 1) ya cubre el gap; documentar.
9. **Compat-audit en el build**: script `scripts/compat-audit` (node) que escanea los chunks compilados de cada app y **falla el build** si detecta APIs de la denylist sin polyfill (usos reales de `.at(`, `Object.hasOwn`, `structuredClone`, lookbehind literales, import attributes, `AbortSignal.timeout`, `findLast`…). Integrado en los builds. **Esto impide que el próximo upgrade de Next/supabase reintroduzca incompatibilidad.**
10. **Service worker legacy-guard**: en nucleo/campo (@serwist, hoy `skipWaiting`+`clientsClaim` auto-inyectado), desactivar el registro en navegadores legacy para evitar stale-cache en dispositivos viejos (register: false + registro manual con guard).
11. **Política de soporte documentada en AGENTS.md**: matriz de compatibilidad (iOS 16+ full; iOS 15.4+ con capa de compat; <15.4 degrada), patrón canónico de viewport (`min-h-screen min-h-dvh`) y referencia al audit.

### Fase 3 — Verificación
12. Unit tests del polyfill pasan; audit pasa en los 3 bundles; builds de las 3 apps limpios (TS strict); curl del HTML confirma script antes de los chunks; `-webkit-backdrop-filter` presente en CSS compilado.
13. **Prueba en el iPhone 7 real** con el harness activo: confirmar el error real → aplicar el fix correspondiente (si el harness muestra un TypeError de X, esa X se polyfillea/fija) → re-verificar en dispositivo.

### Fuera de alcance (documentado)
- Optimización general de peso para 2GB RAM (solo el login si el audit lo justifica)
- Soporte < iOS 15.4 (se degrada con aviso, no se garantiza)

### Riesgo principal (declarado)
El harness puede revelar que el fallo en 15.8 es un crash de pestaña por memoria (no un error JS capturable). En ese caso el plan B (payload reducido del login o entry estático) se activa con el dato en mano, no a ciegas.
